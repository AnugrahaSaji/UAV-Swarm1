- metrics.latency.latency_invalid_reason: missing_system_time_reference
- metrics.mavlink_observability.link_status.state: idle
- metrics.mavlink_observability.link_status.stream_active: false
- metrics.mavlink_observability.link_status.heartbeat_present: false

Why this run was important:
- It looked successful at first glance.
- It was not actually a valid success from a MAVLink data-flow standpoint.
- The benchmark harness had allowed a false-positive success artifact even though:
  - no telemetry packets were observed
  - link was idle
  - heartbeat was absent
  - latency had no valid basis

Root problems identified from this run and neighboring failures:

1. False success artifact generation
   The GCS side could write success=true even when suite activation or traffic
   readiness had not really succeeded.

2. Apparent 4-second handshake inflation
   The reported "handshake" timing mixed together:
   - crypto handshake
   - proxy startup
   - suite activation warmup
   - dwell behavior

3. Chronos sync accounting corruption on the drone side
   Clock sync data was being double-recorded, inflating sync_count and making
   timing interpretation worse.

4. Canonical suite ids vs legacy matrix key directories
   The runtime had moved toward canonical cs-{kem}-{sig} ids, while benchmark
   key-material directory resolution still needed compatibility handling.

Engineering conclusion from this stage:
- The live MAV path was giving useful signals, but the benchmark harness itself
  needed hardening before any of these results could be treated as reliable.

That is the actual end-to-end path in plain sequence:

4. Drone decrypts and delivers them on the local drone side.
5. Drone local MAV/Pixhawk side continues producing telemetry.
6. Drone secure tunnel encrypts that outbound plaintext telemetry.
7. GCS receives and decrypts the returning encrypted telemetry.
8. GCS sniff-port collector and pymavlink observer confirm the recovered live
   MAVLink stream, heartbeat, message types, and latency.

So this was not a one-way encrypt-only proof. The corrected smoke included the
return telemetry leg and the GCS-side recovery/observation of that return leg.

11. Problems Faced and How They Were Overcome
======================================================================

Problem A: False success artifacts in live benchmark runs

Symptom:
- GCS suite JSON could say success=true even when there was no real telemetry flow.

Fix direction:
- benchmark state handling was tightened
- failure conditions now write explicit failure artifacts

Relevant commits:
- 2121717 fix(bench): harden mav benchmark timing and suite state

Evidence:
- bad state example: live_run_20260315_233328
- corrected failure artifact: live_run_20260315_235706

Problem B: Inflated "handshake" timing

Symptom:
- reported ~4 s timings looked cryptographically abnormal

Root cause:
- suite activation overhead and dwell warmup were mixed into the reported timing

Fix/result:
- later smoke separated the real handshake cost from activation warmup
- real handshake shown at 22.820505 ms in the corrected smoke

Problem C: Chronos clock sync double recording

Symptom:
- sync_count and drift interpretation were unreliable

Fix direction:
- benchmark synchronization accounting was cleaned up in the drone path

Relevant commits:
- 2121717 fix(bench): harden mav benchmark timing and suite state

Problem D: Canonical suite ids did not resolve cleanly against old key dirs

Symptom:
- cs-{kem}-{sig} suite identity did not always match legacy on-disk matrix naming

Fix direction:
- compatibility resolution was added so the benchmark path could find the
  correct key material without reverting to older suite modeling

Relevant commit:
- aa28d9a fix(bench): resolve canonical suite keys from legacy matrix dirs

Problem E: MAVLink observability was too shallow

Symptom:
- earlier runs had weaker evidence for actual live link quality

Fix direction:
- GCS sniff-port observability was expanded to export:
  - live message logging
  - link state
  - recent messages
